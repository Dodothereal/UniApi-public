# macOS Fan Control

This is a hardware component of UniApi, not a standalone application. The React page is `client/src/apps/fans`; routes and monitoring are `server/src/apps/fans`; native quick controls are `shell/FanMenu.swift`.

## Build and verification

```sh
native/fans/build.sh
native/fans/verify.sh
data/bin/uniapi-fans --probe
sudo native/fans/install-daemon.sh install "$PWD/data/bin/uniapi-fans" "$(id -u)"   # or press Install helper in Preferences
```

`pnpm rebuild:ui` from the repo root updates the page without restarting the server. With the daemon installed, nothing in the ordinary loop asks for a password: not a UI rebuild, not a server restart, not an app relaunch, not a reboot. Only replacing the installed root-owned binary does — press **Update helper** after `build.sh` if you want the new code live, or leave it, since the running daemon keeps working. Recompiling atomically replaces `data/bin/uniapi-fans` without touching a running helper, which keeps its own inode and safety watchdog either way.

Without the daemon the old rules still apply: explicit Quit, server restart and sleep end a temporary control session, and the next Enable controls asks again.

`build.sh` compiles an ad-hoc signed Swift/IOKit binary into gitignored `data/bin`. `shell/build.sh` builds it too; macOS release packages carry the binary and source/licenses. `verify.sh` runs simulated hardware regressions and compiles the full helper, without requesting privileges or changing fans. The main repository verification and macOS CI run those tests. `--probe` performs live read-only monitoring; `--monitor` emits one bounded JSON snapshot every two seconds.

## Controls people use

- Automatic: macOS controls fans.
- Cooler: start cooling earlier using a monotone temperature curve.
- Boost: each fan’s own maximum for 1, 5, 10 or 30 minutes, then Automatic.
- Manual: drag each dial or type its target RPM and press Set/Enter, within device-reported limits and with a 1–60 minute timer. One Reset to Auto is beside Fan speed.
- Duration: the selector picks the timer for your next dial adjustment, and **Set** applies it to whatever profile is already running, counting from that moment; Never drops the timer and keeps the profile instead, so one control converts in both directions. Boost cannot be untimed, so Set is disabled there for Never rather than sending something the helper refuses. The remaining time counts down live in the overview, the mode badge and the duration row.
- Custom curve: four points editable by graph dragging, keyboard arrows, typed values or optional sliders; temperatures rise by at least 5°C, range percentages never decrease and reach 100% by 90°C.
- Sensors: current/peak readings, search, groups and favorites.
- History: 30-minute through one-year, all-time and custom date ranges; temperature/RPM averages, minima and peaks, hover readouts and CSV export. Raw samples are saved every 10 seconds for up to 7 days, minute summaries for 90 days, hourly for one year, daily indefinitely. Fine tiers compact sooner near a 500 MB target. Monitoring continues with the window closed while the server runs; sleep creates a gap.
- Native menu bar: CPU temperature, RPM, both or icon only; Automatic, Cooler, 5-minute Boost and Open Fan Control. Unit/display preferences are persisted in SQLite. Favorites and the saved curve are local UI preferences.

No login, analytics, cloud sync, health scores, stress-test buttons or unrelated system metrics.

## Lifecycle and privilege contract

Only monitoring runs by default. Controlling fans needs root — `AppleSMC` has no unprivileged write path and macOS publishes no fan API — so the helper runs privileged, in one of two shapes.

**The installed daemon (`--daemon UID`), the normal one.** `install-daemon.sh` asks for the administrator password **once**, copies the helper to `/Library/PrivilegedHelperTools/app.devved.uniapi.fans` (root:wheel, 0755) and installs the LaunchDaemon `app.devved.uniapi.fans`. launchd starts it at boot and keeps it alive; every UniApi server afterwards simply attaches to its socket. No dialog on an app restart, a server restart, a UI rebuild or a reboot. Remove it from Preferences, or with `install-daemon.sh uninstall`.

The binary is **copied**, never pointed at. `data/bin/uniapi-fans` is writable by the logged-in user — it has to be, an ordinary build produces it — and a LaunchDaemon executing a user-writable file as root is a local privilege escalation: anything running as that user owns the machine at the next boot. That is also the honest reason rebuilding the helper costs one more password: there is no way to let unprivileged code update a root-executed binary that is not the same hole. An ad-hoc signature is no defence, because whoever could overwrite the file can ad-hoc sign their own. The Preferences row says "Update helper" when the installed copy's SHA-256 differs from the build in `data/bin`; that mismatch is informational, since identical bytes are the only way to be sure two builds agree on the wire and the running daemon still speaks it. `tools/pentest.py:repo-10` fails if the installed copy, its plist or any of their parent directories is ever user-writable, a symlink, or points root at a path inside `$HOME`; `src-fan-install` pins the installer's own refusals.

**The temporary session (`--serve UID SERVER_PID`), the fallback.** What Enable controls did before, and still does when no daemon is installed: one administrator dialog per server process, scoped to that process, gone when it exits. Offered as "Just this session" in Preferences for anyone who would rather not have a standing root service.

A socket under `/var/run/app.devved.uniapi.fans-UID/` is private to the owner UID, with a root-owned non-writable parent. A session's socket is named after the server process it belongs to; the daemon's is the fixed `control.sock`, so no server PID can ever collide with it. A session additionally checks the kernel-reported peer PID against the UniApi Node server. **The daemon cannot**, and does not: it outlives every server process, so there is no owner PID to bind to, and `getpeereid` is the whole check. That is a real widening, stated plainly — with the daemon installed, any code already running as you can drive the fans without a password, where before it would have had to wait for you to type one. What still holds is everything the command surface is made of: a fixed six-word vocabulary with no key names, paths, shell or network; per-fan reported limits; the thermal floor and releases below; and the helper's own heartbeat lease. The worst a local attacker gains is noisy or slow fans within those bounds, on a machine where they could already have asked you for the password with a dialog indistinguishable from ours. `docs/SECURITY.md` carries the same statement.

Manual duration zero means Never: no timer, no `until` in its reply. Boost remains timed (10–3600 seconds). The helper has a 10-second heartbeat lease, optional manual timer expiry, per-fan limits, a hottest-sensor cooling floor in every mode and actual-RPM verification. A changing curve target does not reset its stalled-fan timer. Session processor-sensor IDs are frozen, but a frozen sensor going missing only releases when it was **at least as hot as the reading being steered by** - that is the case where losing it would silently under-cool from a cooler sensor, which is what the rule exists to prevent. Apple Silicon parks idle cores and a parked core reports a low single-digit sentinel that `Hardware.snapshot` drops as invalid, so sensors come and go all day on an ordinary machine; releasing on any disappearance flapped a curve to Automatic and back every time a core went to sleep (observed 2026-09-13: 33 sensors to 31 and back). Cooler sensors that vanish are dropped from the frozen set and the override continues. **Heat never returns system control.** It used to, at 105°C and at serious macOS thermal pressure, and that is the one response measured to make things worse - see the thermal section below. A hot machine gets the 100% floor instead. What still releases is the set of conditions that mean the helper cannot do its job: no CPU or GPU reading at all, a lost heartbeat, an expired timer, fans that are absent or report impossible limits, a stalled fan, sleep, or an explicit Automatic.

**Kept profiles.** The helper itself still holds nothing: every release path below hands the fans back, and waking never resumes an override by itself. What persists is the *intent*, in the server's `fans_keep` table, and only for profiles that named no end — Cooler, a custom curve, and manual with duration Never. That is read off the *duration*, not the command name, because Cooler and a curve accept one too: keeping them unconditionally marked a profile the user had explicitly given a timer as Kept, and the page then showed a one-minute selection beside an infinity badge describing the same profile. A boost or a timed manual speed asked to finish, so remembering it would override a decision the user already made; Automatic is a stop and clears the row. The server re-sends a kept profile whenever the helper reports Automatic, and the spacing is keyed on how long the last attempt **survived**, not on whether the command was accepted. That distinction is the whole safety of the mechanism. Several of the helper's releases are re-armed by the act of re-applying: `Controller.handle` clears `mismatchSince` on every accepted command and cannot re-check the 20-second stalled-fan condition, so a fan that physically cannot reach its commanded speed gives accept, release 20 seconds later, accept again - forever, at roughly a 90% duty cycle, with an acceptance-keyed backoff pinned at its minimum. That silently defeats exactly the recovery the helper exists to provide. `releaseBackoff` doubles the wait for an override that held under two minutes and resets it for one that held longer, so a persistent fault decays to one brief attempt every five minutes while a thermal spike still comes back promptly. The next attempt is scheduled from the *observed release*, not from the last attempt - anchored to the attempt, a 20-second failure always lands after the 15-second floor has already elapsed and the backoff never grows. The same anchoring is what stops a profile re-forcing the fans in the window between the sleep release and the actual suspend. The row is re-validated through the same `validateCommand` a live request passes, because it is replayed straight at a root helper after a restart.

One consequence worth stating: with a kept profile the ten-second client lease no longer applies. Without one the old rule stands — no page and no menu asking for status in ten seconds means nobody is watching, so the server hands the fans back. A kept profile *is* the watcher; the server (a KeepAlive LaunchAgent) holds it, and the helper's own heartbeat lease still ends the override if that server dies. `pollAction` in `server/src/apps/fans/types.ts` is that decision, pure and unit-tested, because getting it wrong is either a fan stuck on or a fan that quietly forgets. Quitting the window is no longer a fan instruction either: it used to POST `/release`, which now also retires the kept profile, so it would have thrown away the thing the user asked the app to remember. Choose Automatic to actually stop.

Cooler and custom curves are evaluated against the readings the overview shows: the higher of the CPU die average (TCMb) and the hottest GPU sensor (`Snapshot.governing`), smoothed with a 4-second exponential time constant (ticks land 1-2 s apart depending on IPC traffic, so the factor is time-based) so a one-tick spike does not ratchet the fans up (rises are immediate, decreases are slewed at 120 RPM per tick). A 60°C to 90°C step therefore reaches most of its output after about 10 s; the floor and the releases below use the raw reading and are never delayed. Without a TCMb key (Intel Macs) the CPU reading is the hottest CPU sensor, exactly as the overview shows it. The hottest single sensor, including the CPU die maximum TCMz, steers speeds only through the emergency floor: a continuous ramp from 0% just above 95°C to 100% at 100°C, in every mode including manual, evaluated on a 2-second smoothed reading so a one-sample spike cannot jump the fans; **no release is keyed to temperature at all, and that is deliberate.** Both thermal releases have now been removed, and the measurement that settles it was taken on this M4 Pro on 2026-09-13: across six hours of saved history, 31 buckets recorded a CPU die *average* at or above 100°C, peaking at 108.3°C, and on every one of them macOS was running the fans between 2325 and 3181 RPM against a 7826 RPM ceiling. A user watched their machine sit at 107°C with the fans at 2348 RPM because the helper had politely handed them back. "It is too hot, let the system take over" gives the hottest moment to a system that does essentially nothing. Holding is strictly better: the floor is already at 100% by 100°C, and full airflow cannot harm anything. Serious thermal pressure is treated the same way - the OS throttling is a reason to blow harder, not to leave. Verified after the change on the same machine: with a curve held through TCMz crossing 105°C four times, the fans ran 7779-7865 RPM and the die average peaked at 98.4°C rather than 107°C. The two earlier attempts at this are worth knowing about, because both looked right: first the release was raw, which fired on spikes (TCMz peaked at 115.9°C twenty-six times in one hour while macOS drove the fans) and flapped a curve to Automatic every couple of minutes; then it was made *sustained*, which stopped the flapping and produced the 107°C machine with idle fans, because sustained heat is exactly when it must not let go. The ramp is continuous because the die maximum crosses 95°C hundreds of times a day under macOS's own fans (24 h of history on 2026-09-06: 317 crossings, 6.0% of samples above 95°C) and a stepped floor would ratchet just like the old curve. Until 2026-09-06 both the curves and an 85°C floor were keyed to that hottest sensor. On Apple Silicon it idles near 80°C and reaches the mid-90s under macOS's own minimum-RPM automatic control, so every profile pinned the fans at full speed while the page showed a 63°C average, whatever the curve said.

Apple Silicon target registers can lag a successful write by about a second. Both targets are written before a bounded three-second confirmation wait. Successful acquisition renews the heartbeat; the IPC timeout covers acquisition plus one restoration attempt.

Restoration intent is latched before hardware writes. If restoration fails, the helper retries rather than resuming the previous mode. Failed cleanup retains the watchdog with bounded backoff until restoration is verified. IPC failures are shown as recovery pending, not a false Automatic state. Sleep is handled directly through IORegisterForSystemPower before acknowledging sleep, with a suspend-discontinuity fallback. It ends the session; queued overrides do not resume after waking. Server exit releases ownership through the helper's owner-process check.

The native menu polls status even when the window closes. A browser-only session with **no kept profile** loses its client lease when the page stops polling, so leaving the page returns Automatic; a kept profile is held regardless, which is what the user asked for when they chose it. Permission to monitor or control is still never *itself* a request to resume anything — what resumes is a profile the user explicitly asked to keep, and only that. This retires the older rule that nothing auto-resumes after a restart; it was a safe default, not a property anyone depended on, and it made "hold my fans here" impossible to express.

## Research and hardware observations

Research on 2026-09-05 used the user's Research CLI, TinyFish search/fetch and primary-source inspection:

- [Macs Fan Control](https://crystalidea.com/macs-fan-control): automatic/custom modes, temperature-based presets, menu readings and Auto on quit informed the task flow.
- [TG Pro guide](https://www.tunabellysoftware.com/support/tgpro_tutorial/): sensor grouping, session peaks, two-second updates, menu display and exports are useful; email and extensive rule automation were omitted.
- [ThermalForge](https://github.com/ProducerGuy/ThermalForge): low-level SMC transport adapted under MIT, with firmware-result and payload-size validation added. Its license and the original [macos-smc-fan](https://github.com/agoodkind/macos-smc-fan) MIT notices are in Resources.
- [SMC research](https://github.com/agoodkind/macos-smc-fan/blob/main/docs/research.md) and [Stats issue 2928](https://github.com/exelban/stats/issues/2928): mode writes can be blocked by firmware even when IOKit returns success. Ftst unlock and mode/target readback are required; actual fan response is checked too.
- [OSHI sensor plausibility tests](https://www.oshi.ooo/xref-test/oshi/ffm/MacSensorsPlausibilityFFMTest.html): idle core keys can return low single-digit sentinel readings. TCMb is die average, TCMz is maximum. GPU keys are discovered dynamically.
- [Stats sensor definitions](https://github.com/exelban/stats/blob/master/Modules/Sensors/values.swift): known auxiliary sensors and optional named HID categories. HID returned no processor readings on the local macOS build; the firmware aggregates are essential.

Observed 2026-09-06 on the same M4 Pro over 24 h of raw 10-second history (7797 samples) under macOS automatic control at roughly 2315-3362 RPM: TCMz p10 79.2°C, median 89.5°C, p90 94.4°C, p99 100.2°C, maximum 115.7°C (with TCMb at 99.9°C and the fans at 3070/3314 RPM, still automatic). At a true idle (TCMb at or below 60°C) TCMz sat at 61.3-65.9°C, and at a 64°C average it swung between 62°C and 78°C within ten seconds. The die maximum is a protection input, not a control input; those percentiles are what justify the 95°C ramp. They also rule out any release keyed to it - a threshold the sensor crosses hundreds of times a day under Apple's own fan control is not a distress signal.

Sensor discovery happens once per helper process and filters on key existence and type, never on the value it reads at that moment. That distinction only became load-bearing when the helper became a LaunchDaemon: started on demand the machine was warm, started at boot the GPU is parked and every `Tg*` key reports the sub-10°C idle sentinel, so a value filter dropped the entire GPU group permanently and the daemon spent its whole life unable to see a GPU temperature - refusing every acquisition as "blind" while the machine sat at 107°C with idle fans. `snapshot()` drops sentinels per read, which is the right place for it.

Local read-only verification: Mac16,8 / Apple M4 Pro / macOS 27.0 (26A5425a), two fans, device-reported 2317–7826 RPM each, 33 valid sensors. CPU headline uses TCMb average; protection also watches TCMz maximum. Values below 10°C are treated as unavailable sentinels. Accessory sensors use known keys; unknown temperature-shaped keys are not automatically labeled CPU cores. No machine serial or hardware UUID is collected.

Other Macs are capability-detected, not certified by this local run. Fanless Macs show an explicit empty fan state. Control requires both CPU and GPU temperatures. IOKit/SMC interfaces are not public supported fan-control APIs; a future OS update may require compatibility work.

See `docs/FAN-VERIFICATION.md` at repository root for the exact tests and live validation completed in this change.

## UI interaction fixture

Build the client, then run from the server directory:

    pnpm exec tsx test/ui-fixture.ts

Open localhost port 8781. Fan commands validate and update simulated state only;
all other mutations are refused. GET /__fixture reports commands and request
counts for dial, curve and navigation tests. Other app GET requests use the
running local server; the fixture does not provide WebSocket streaming. Stop it
with Ctrl-C. This supplements the helper's simulated hardware suite and a real
read-only probe; it does not claim that a browser drag physically changed a fan.
